1. НАЗНАЧЕНИЕ И ЧТО ДЕЛАЕТ СЕРВИС
================================================================================

На вход подаётся один файл GeoJSON, в котором лежат:
  - существующая тепловая сеть (линии и камеры),
  - точки подключения объектов капитального строительства (ОКС) с расходом в т/ч,
  - пространственные ограничения: здания, дороги, трамвайные пути, газопроводы,
    силовые кабели, водные объекты, железные дороги, парки, запретные участки.

Сервис строит новую тепловую сеть, которая соединяет все точки ОКС с существующей
сетью, подбирает диаметры, считает стоимость и выдаёт до трёх различающихся
вариантов, отранжированных по целевому показателю S.

Результат отдаётся в GeoJSON по формату раздела 7 технического задания: линейные
участки с диаметром, расходом, стоимостью и способом прокладки; камеры и врезки;
технические узлы на границах специальных переходов; сводка по варианту с проверкой
правил. Дополнительно строится вариант с глубинами заложения (продольный профиль).

Показатель качества:

    S = 0,7 * C / 25 000 000 + 0,3 * L / 100

где C - полная стоимость строительства в рублях, L - длина новой сети в метрах.
Чем меньше S, тем лучше. Неподключённые ОКС штрафуются отдельно.

2. СООТВЕТСТВИЕ ТЕХНИЧЕСКИМ ОГРАНИЧЕНИЯМ ЗАДАНИЯ
================================================================================

  - Язык: Java 11. Весь расчёт - детерминированные алгоритмы вычислительной
    геометрии и комбинаторной оптимизации.
  - Машинное обучение и нейросети не используются ни на одном шаге. В зависимостях
    нет ни одной ML-библиотеки, обученных моделей в поставке нет.
  - Сборка и запуск одной командой через docker compose. Поставка идёт готовыми
    образами, интернет при развёртывании не нужен.
  - Никаких данных из тестового набора в коде нет. Все пороги, диаметры, отступы,
    стоимости и коэффициенты вынесены в конфигурацию (application.yml) и берутся
    из таблиц технического задания, а не из конкретного файла с данными.
    Направление сетки квартала, зоны поиска, классы отступов - всё вычисляется
    из входного файла в момент расчёта.
  - Работа без интернета: карта, библиотека Leaflet и стили лежат внутри
    приложения, подложка по умолчанию отключена.

Пакеты (ru.lct.heat.*):

  ingest      потоковая загрузка GeoJSON, диагностика данных, запись в PostGIS
  model       правила и параметры из конфигурации, модель сценария

  config      конфигурация (все числа из таблиц ТЗ)

Конвейер:

  1. Загрузка       потоковый разбор GeoJSON, пересчёт в метрическую систему
                    координат EPSG:32637, пакетная запись в PostGIS
  2. Подготовка     топология существующей сети, зона поиска, собственные
                    полигоны ОКС, точки выхода из зданий
  3. Препятствия    слои запретных зон по классам диаметров: буферы с отступами
                    из таблицы 2, мягкие зоны специальных переходов
  4. Маршрут        граф видимости или сетка квартала + поиск A* по состоянию
                    (предыдущий узел, текущий узел) с ограничением угла поворота
  5. Дерево         жадная вставка ОКС по полной цене прироста S, локальный поиск
                    «удалить и вставить заново», LNS «разрушить и собрать»
  6. Диаметры       подбор по накопленному расходу, монотонность вдоль потока,
                    проверка предельной длины, перепроверка отступов новым ДУ
  7. Отделка        спрямление трассы, подтяжка узлов, разбиение на участки
                    базовой и специальной прокладки, стоимость и S
  8. Проверка       независимый валидатор по исходной геометрии
  9. Выход          GeoJSON по разделу 7 ТЗ, до трёх вариантов на режим


================================================================================
5. АЛГОРИТМЫ
================================================================================

5.1 Пространство допустимых положений трубы

Для каждого класса диаметра строится свой слой препятствий: полигоны ограничений
расширяются на требуемый отступ плюс половина ширины трубы. Используются буферы
с соединением MITRE, исправление геометрии (GeometryFixer) и упрощение
(TopologyPreservingSimplifier). Поиск по слою идёт через пространственный индекс
STRtree и подготовленную геометрию (PreparedGeometry).

Специальные переходы (дороги, трамвайные пути, газопроводы, кабели, пересечение
существующей сети) не запрещают участок, а удорожают ту его часть, которая
попадает в зону: коэффициент K_спец из таблицы 2. Границы этой части считаются
параметрически, без тяжёлых булевых операций.

5.2 Поиск маршрута

Граф видимости строится по вершинам препятствий с ограничением радиуса. Поиск -
A* по рёберному состоянию: вершина поиска это пара (откуда пришли, где стоим).
Это позволяет проверять угол поворота на каждом шаге и запрещать повороты круче
90 градусов (R-GEO-02). Эвристика: расстояние по прямой, умноженное на
минимальную цену метра, плюс минимальная цена узла. В монтажном режиме вместо
графа видимости используется регулярная решётка, повёрнутая по направлению
застройки квартала.

5.3 Построение дерева

Задача близка к задаче Штейнера на графе с переменными диаметрами, она
NP-трудна, поэтому используются эвристики:

  - базовое решение «звезда»: каждый ОКС подключается отдельно;
  - жадная вставка: ОКС добавляется туда, где прирост полной цены S минимален,
    при этом учитывается рост диаметров вверх по потоку и новые камеры;
  - локальный поиск: ОКС вынимается и вставляется заново, ход принимается,
    только если S уменьшился;
  - LNS «разрушить и собрать»: вынимается группа соседних ОКС и вставляется
    в случайном порядке; выводит из локальных оптимумов;
  - несколько стартов с разным порядком обхода (по расстоянию, по расходу,
    с другой врезкой) дают пул решений, из которого отбираются варианты.

Отбор вариантов: решения сортируются по S, вариант берётся в выдачу, только если
он содержательно отличается от уже выбранных - площадь пересечения коридоров
шириной 5 м не превышает заданной доли.

5.4 Подбор диаметров

Расход накапливается от листьев к врезке. По таблице 1 выбирается минимальный
диаметр, пропускающий этот расход; диаметр не убывает вниз по потоку; проверяется
предельная длина L_max для диаметра - при её превышении диаметр увеличивается,
и так до устойчивого состояния. После роста диаметра растут и отступы, поэтому
геометрия перепроверяется, а при необходимости трасса перестраивается.

5.5 Отделка

  - Спрямление: участок между двумя вершинами заменяется прямой, если она
    допустима и углы остаются в норме. Пробуется сначала самый длинный кусок:
    удаления по одной вершине не хватает, потому что промежуточный вариант может
    быть недопустим, хотя убрать ступеньку целиком можно.
  - Подтяжка узлов: камера ветвления переезжает туда, где продолжение подходящей
    к ней трассы встречает соседнюю ветку. Так исчезают короткие «крючки» перед
    врезкой. Переезд принимается, только если все примыкающие участки остаются
    допустимыми и S уменьшается.
  - Отделка выполняется дважды: до подбора диаметров и после него, потому что
    при росте диаметра часть трассы перестраивается заново.

6. ПРАВИЛА ЗАДАЧИ И КАК ОНИ ЗАДАНЫ
================================================================================

Все правила технического задания реализованы и помечены кодами (R-...):
топология сети, врезки в существующую сеть и камеры, отступы от объектов,
специальные переходы, углы поворота, ввод в здание, неподключённые ОКС.

Числовые параметры лежат в application.yml внутри образа:

  pipes                таблица 1: ДУ, предельный расход, L_max, стоимость метра,
                       ширина и высота канала
  restrictions         таблица 2: тип объекта -> запрет или специальный переход,
                       отступ (в том числе по диапазонам ДУ), K_спец, правила
                       вертикали и глубины
  chambers             стоимость камер по ДУ, максимум примыканий, радиус
                       привязки к существующей камере, минимум до пересечения
  geometry             максимальный угол поворота, радиус видимости, допуски
  score                веса и нормировки показателя S, штрафы
  solver               бюджет времени, число стартов, зерно генератора
  variants             сколько вариантов выдавать и насколько они должны отличаться
  depth                параметры режима с глубиной
  installation         параметры монтажного режима

Любой параметр переопределяется переменной окружения или подменой файла, править
код для этого не нужно.


================================================================================
7. ДВА РЕЖИМА ТРАССИРОВКИ
================================================================================

7.1 Экономичный (economy)

Минимизируется показатель S. Углы поворота любые в пределах 90 градусов, трасса
идёт по кратчайшему допустимому пути вокруг препятствий. Это базовый режим,
соответствующий постановке задания.

7.2 Монтажный (installation)

Дополнительные правила, удобные для строительства. Все они строже обязательных
требований задания и не нарушают их.

  1) Углы только 45 и 90 градусов. Базовое направление - преобладающее
     направление стен зданий квартала (считается из данных), либо задаётся
     вручную. Узлы графа - точки решётки с шагом 8 м, повёрнутой на это
     направление, ходы в 8 соседей. Исключения, без которых нарушалось бы
     задание: финальный отрезок ввода в здание (он идёт к ближайшей точке стены)
     и короткая перемычка до узла или точки врезки не длиннее полутора шагов
     решётки.
  2) Без параллельных прокладок. Участок, идущий ближе 15 м к другой трубе под
     углом меньше 20 градусов, получает восьмикратный штраф при поиске, поэтому
     выгоднее сделать врезку рядом, чем вести трубу вдоль. Работает и против
     существующей сети, и против собственных веток.
  3) Вдоль улиц. Полоса шириной 12 м сразу за зоной отступа дороги считается
     удобным коридором, цена поиска в ней умножается на 0,75. Внутрь полигона
     дороги трасса не заходит, дорога по-прежнему пересекается только поперёк.

На конкурсном наборе около 87 процентов длины трассы ложится строго по сетке
квартала, остальное - обязательные вводы в здания и короткие перемычки.

Оба режима считаются в одном запуске, результаты помечены полями routing_mode
и routing_mode_name, идентификаторы вариантов начинаются с e (экономичный) и
m (монтажный).


================================================================================
8. РЕЖИМ С ГЛУБИНОЙ ЗАЛОЖЕНИЯ
================================================================================

Для лучшего варианта дополнительно строится продольный профиль: глубина в начале
и конце каждого участка, ограничения на уклон, минимальную и нормальную глубину,
правила прохода над или под коммуникацией (газопровод, кабель, существующая
сеть) с нормативным зазором. Стоимость корректируется коэффициентом глубины
K_гл. На границах специальных переходов ставятся технические узлы. Результат
выгружается отдельным файлом (параметр mode=depth).


================================================================================
9. НЕЗАВИСИМАЯ ПРОВЕРКА РЕЗУЛЬТАТА
================================================================================

Готовый вариант проверяется отдельным модулем, который не использует внутренние
структуры решателя и работает по исходной геометрии входного файла. Проверяются:

  - отступы от всех объектов по таблице 2 с учётом итогового диаметра,
  - углы поворота,
  - углы пересечения дорог и трамвайных путей,
  - древовидность и отсутствие касаний участков вне узлов,
  - число примыканий в камерах, правила врезки,
  - проход трубы сквозь здания, в том числе своё,
  - монотонность диаметров и предельные длины.

Найденные нарушения попадают в поле validation_errors соответствующего варианта.
На конкурсном и демонстрационном наборах нарушений нет ни в одном режиме.


================================================================================
10. ФОРМАТ ВЫХОДНЫХ ДАННЫХ
================================================================================

FeatureCollection, объекты:

  heat_network    линейный участок новой сети. Свойства: id, variant_id,
                  start_node_id, end_node_id, flow_tph, diameter, length,
                  laying_method (base или special), depth_start, depth_end,
                  cost, special_restriction_types, k_spec
  heat_chamber    камера: новая врезка (chamber_role = tie_in), камера ветвления
                  (branch) или технический узел; diameter, cost, tie_in_line_id
  variant_summary сводка варианта: rank, strategy, score, calculated_cost,
                  pipe_cost, chamber_construction_cost, new_network_length,
                  new_chambers, tie_ins, unconnected, unconnected_reasons,
                  validation_errors, notes, routing_mode, routing_mode_name

В конец коллекции добавляется поле summary: время расчёта, статистика разбора
входного файла, диагностика и сводка по каждому режиму.

Система координат выдачи - EPSG:4326 (широта и долгота), расчёт ведётся
в EPSG:32637.

11. HTTP API И SWAGGER
================================================================================

Swagger UI:   http://<хост>:8090/swagger-ui.html
Health:       http://<хост>:8090/actuator/health
Веб-карта:    http://<хост>:8090/

11.1 Расчёт одним запросом (без базы данных)

Файл на входе, готовый GeoJSON в ответе. Подходит для интеграции: ждать статус
не нужно, обращений к базе нет.

  POST /api/routing/economy         только экономичный режим
  POST /api/routing/installation    только монтажный режим
  POST /api/routing/all             оба режима в одном файле

  Тело: multipart/form-data, поле file
  Параметр: ?budgetSeconds=60 - бюджет времени на режим (необязательный)
  Ответ: GeoJSON (application/geo+json)

  Пример:
    curl -F "file=@dataset.geojson" \
         "http://localhost:8090/api/routing/all?budgetSeconds=45" -o result.geojson

11.2 Асинхронный расчёт (для файлов в сотни мегабайт и больше)

Входной файл пишется на диск и в базу потоково, расчёт идёт в очереди.

  POST   /api/datasets                       загрузка файла (multipart, поле file)
  GET    /api/datasets                       список загруженных наборов
  GET    /api/datasets/{id}                  статус набора (READY, ERROR и т. д.)
  GET    /api/datasets/{id}/summary          статистика разбора и диагностика
  GET    /api/datasets/{id}/geojson          исходные данные набора
  POST   /api/datasets/{id}/solve            запустить расчёт
                                             (?budgetSeconds=120)
  GET    /api/datasets/{id}/solutions        список расчётов по набору
  GET    /api/solutions/{id}                 статус и сводка расчёта
  GET    /api/solutions/{id}/geojson         результат
                                             (?download=true, ?mode=2d|depth)

  Пример полного цикла:
    ID=$(curl -s -F "file=@dataset.geojson" localhost:8090/api/datasets | jq -r .id)
    curl -s localhost:8090/api/datasets/$ID | jq .status
    SID=$(curl -s -X POST localhost:8090/api/datasets/$ID/solve | jq -r .id)
    curl -s localhost:8090/api/solutions/$SID | jq .summary
    curl -s "localhost:8090/api/solutions/$SID/geojson?download=true" -o result.geojson


================================================================================
12. ВЕБ-КАРТА
================================================================================

По адресу http://<хост>:8090/ открывается карта на Leaflet. Возможности:

  - загрузка GeoJSON и запуск расчёта;
  - переключение режимов «Экономичный» и «Монтажный» (считаются оба);
  - выбор варианта из списка, таблица со стоимостью, длиной, S и результатом
    проверки правил;
  - слои: ограничения, существующая сеть, точки ОКС, новая сеть; легенда
    с цветами по диаметрам, отдельно показаны специальные переходы, камеры,
    врезки и технические узлы;
  - выгрузка результата в файл;
  - кнопка «Демо-набор» загружает демонстрационный набор с дорогами
    и газопроводом, на нём видны специальные переходы.

Интернет не требуется: библиотека карты лежит внутри приложения, подложка по
умолчанию отключена, на карте только данные проекта. Подложки OpenStreetMap
и Esri доступны как необязательный вариант, для них нужен интернет.


================================================================================
13. РАЗВЁРТЫВАНИЕ
================================================================================

Целевая платформа: linux/amd64, Docker 20.10 или новее, docker compose
(подойдёт и docker-compose 1.29.2). Рекомендуется 16 ГБ оперативной памяти,
приложению по умолчанию выделяется 2 ГБ кучи.

  1. Проверить целостность архивов:
       sha256sum -c sha256sums.txt

  2. Загрузить образы в Docker:
       docker load -i heat-routing-1.1.0-amd64.tar.gz
       docker load -i postgis-16-3.4-amd64.tar.gz

  3. Запустить из папки с docker-compose.yml:
       docker compose up -d
       (для docker-compose 1.29.2:  docker-compose up -d)

  4. Проверить:
       curl -s localhost:8090/actuator/health      ожидается {"status":"UP"}

Первый запуск занимает около 30 секунд: база создаёт кластер, приложение
накатывает схему. Сборка на целевой машине не нужна, интернет не нужен.

Остановить:            docker compose down
Удалить вместе с базой: docker compose down -v

14. НАСТРОЙКА
================================================================================

Переменные окружения при запуске, например APP_PORT=8080 docker compose up -d:

  APP_PORT      8090          порт, на котором отвечает сервис
  DB_PASSWORD   heat          пароль базы данных
  JAVA_OPTS     -Xmx2g        параметры JVM, для больших файлов -Xmx4g

Тома:

  db-data       база данных (загруженные наборы и результаты расчётов)
  uploads       временный диск для входных файлов (вход до 3 ГБ читается потоком)

Параметры расчёта лежат внутри образа в application.yml. Их можно
переопределить переменными окружения вида HEAT_SOLVER_TIMEBUDGETS=90 или
подменить файл целиком:

  -v /путь/application.yml:/app/config/application.yml

15. ПРОИЗВОДИТЕЛЬНОСТЬ И РЕЗУЛЬТАТЫ
================================================================================

Замеры на рабочей машине (общая, под нагрузкой другими задачами):

  Загрузка файла 331 МБ          32 секунды, пик памяти около 533 МБ
  Конкурсный набор (17 ОКС)      45 секунд на режим, 3 варианта
  Синтетический квартал
  (1600 зданий, 78 ОКС)          60 секунд, нарушений правил 0

Конкурсный набор, результат:

  подключены все 17 ОКС, неподключённых нет
  нарушений правил 0 в обоих режимах
  экономичный режим: лучший S около 13,3
  монтажный режим:   лучший S около 14,6, около 87 процентов длины по сетке

Время расчёта ограничивается бюджетом (параметр budgetSeconds или настройка
solver.time-budget-s): алгоритм улучшает решение, пока есть время, и всегда
возвращает корректный результат по истечении бюджета.


================================================================================
16. ДОПУЩЕНИЯ И ГРАНИЦЫ ПРИМЕНИМОСТИ
================================================================================

Ответы организаторов от 24.09.2026 учтены: минимального расстояния между новыми
участками нет; обход коммуникации по глубине допустим; предпочтения существующим
камерам нет; отступы отсчитываются от центральной линии полигона; неизвестный тип
ограничения игнорируется (настраивается параметром unknown-restriction).

Оставшееся допущение: если ближайшая к точке ОКС точка границы здания не даёт
маршрута (например, выводит в замкнутый двор или в щель между крыльями здания),
точка выхода сдвигается по стене до первой рабочей. Без этого часть ОКС
невозможно подключить. Каждый такой случай пишется в notes варианта, и в выдаче
видно, где применялось.

Границы применимости:

  - входные данные должны быть в EPSG:4326; другие системы координат
    не пересчитываются;
  - расчёт рассчитан на район или квартал; для очень больших территорий
    нужен бюджет времени больше 60 секунд;
  - высотные отметки поверхности не используются, профиль строится от нормальной
    глубины заложения;
  - гидравлический расчёт сети (давление, потери напора) в задачу не входит:
    диаметры подбираются по расходу и предельной длине из таблиц задания.
