## 1. Суть задачи в одном абзаце

Есть существующая тепловая сеть (линии и камеры) с одним источником и набор точек подключения новых зданий (ОКС), для каждой задан расход в т/ч. Нужно **автоматически** построить новую **древовидную** сеть, которая присоединяет все точки к существующей сети. Для этого сервис выбирает точки врезки, объединяет ОКС в общие ветки, строит трассу по плану (2D) с обходом или спецпересечением препятствий, подбирает диаметры по расходу и предельной длине, считает стоимость и выдаёт до 3 различающихся вариантов, отранжированных по показателю `S`. Результат выгружается в GeoJSON.

## 2. Входные данные

### 2.1. Формат
| Параметр | Значение |
|---|---|
| Формат | один GeoJSON `FeatureCollection` |
| CRS входа/выхода | WGS 84, EPSG:4326 (в датасете `CRS84`: порядок lon, lat) |
| CRS расчётов | **EPSG:32637** (UTM 37N): все длины, расстояния, габариты, углы |
| `id` | string **или** number, используется только как ключ связи, по формату не интерпретируется, тип сохраняется на выходе |
| Размер входа | до 3 ГБ, обработка потоковая, с временным диском, файл целиком в RAM не грузить |

### 2.2. Сущности (`object_type`)
| Сущность | `object_type` | Геометрия | Обязательные атрибуты |
|---|---|---|---|
| Источник | `source` | Point | `id`, `object_type` |
| Существующая теплосеть | `heat_network` | LineString | `id`, `object_type`, `diameter` (мм) |
| Существующая камера | `heat_chamber` | Point | `id`, `object_type` |
| Точка подключения ОКС | `oks_connection_point` | Point | `id`, `object_type`, `flow_tph` (т/ч) |
| Пространственное ограничение | `restriction` | LineString / MultiLineString / Polygon / MultiPolygon | `id`, `object_type`, `restriction_type` |

- **R-IN-01.** Каждая `oks_connection_point` - самостоятельная цель подключения, даже если несколько точек лежат в одном полигоне ОКС.
- **R-IN-02.** Полигоны зданий (и существующих, и перспективных) приходят как `restriction` с `restriction_type = oks`. Связи «точка ↔ полигон» по id нет: её определяем геометрически (точка внутри полигона или на его границе).
- **R-IN-03.** Копию входа можно дополнять своими `restriction` для демо, а неизвестные `restriction_type` допустимы (обработка по конфигу, по умолчанию предупреждение в диагностике).
- **R-IN-04.** Дополнительные properties (например, `address`, `name`) допустимы, их игнорируем.
- **R-IN-05.** Топология существующей сети (кто с кем связан, где камеры на линиях) во входе **явно не задана**, её надо восстановить геометрически (snap концов линий и камер с допуском).

### 2.3. Что в конкурсном датасете (для ориентира, в код не зашивать)
| Тип | Кол-во | Примечание |
|---|---|---|
| `source` | 1 | |
| `heat_network` | 29 | ДУ: 400 ×22, 500 ×6, 300 ×1 |
| `heat_chamber` | 9 | |
| `oks_connection_point` | 17 | `flow_tph` от 4,08 до 76,27, сумма ≈ 488,7 т/ч |
| `restriction: oks` | 85 | MultiPolygon, есть `address` |
| `restriction: water` | 2 | MultiPolygon |
| `restriction: railway` | 1 | MultiPolygon |

Проверочный набор будет **другим** (выгрузка из рабочих систем, иное число объектов и сложность геометрии), поэтому нужно поддержать все типы из таблицы 2 (раздел 5).

## 3. Правила построения новой сети

### 3.1. Топология
- **R-TOP-01.** Одна линия = пара труб (подача + обратка) одного ДУ. Расход пары **не удваивается**.
- **R-TOP-02.** Новая сеть - **лес деревьев**: каждая связная часть присоединяется к существующей сети **ровно в одной точке**. От врезки до каждой точки ОКС ровно один путь, без циклов.
- **R-TOP-03.** Несколько ОКС могут делить общий участок (магистраль → ветки).
- **R-TOP-04.** **Разветвление только в тепловой камере.** Обычный поворот камеры не требует.
- **R-TOP-05.** К камере примыкает **≤ 4 линейных участков**, из них 1 в сторону источника и ≤ 3 в остальные. Каждый участок, заканчивающийся в камере, считается отдельным примыканием. Существующая линия, проходящая сквозь камеру, занимает **2** примыкания.
- **R-TOP-06.** Новые участки **не пересекаются** между собой вне общего узла. При пересечении их объединяют в общую сеть или перестраивают.
- **R-TOP-07.** Вся новая сеть считается магистральной, отдельного «теплового ввода» нет.
- **R-TOP-08.** Узлы новой сети: `oks_connection_point` (лист), `heat_chamber` (новая или существующая), `technical_node`. Отдельный объект `tie_in` **не создаётся**.

### 3.2. Геометрия трассы
- **R-GEO-01.** Трасса строится из прямых отрезков с поворотами в вершинах.
- **R-GEO-02.** Угол поворота (отклонение от продолжения предыдущего отрезка, 0° = прямо) **≤ 90° включительно**, в диапазоне 0-90° угол произвольный. Надбавки за поворот нет.
- **R-GEO-03.** Минимальная длина прямого участка не задана, но **запрещены** необоснованные мелкие изломы, зигзаги и «лесенки». Число поворотов оценивают эксперты, значит нужна постобработка-спрямление.
- **R-GEO-04.** Поворот без смены параметров - внутренняя вершина LineString, отдельный узел не нужен.
- **R-GEO-05.** `technical_node` ставится только там, где без разветвления кончается один участок и начинается другой: смена `laying_method`, ДУ, профиля глубины, набора пересекаемых ограничений. Стоимости у него нет, для разветвления его не используют.
- **R-GEO-06.** Границы области поиска нет, но явно избыточный уход за охват входных объектов считается некорректным. Практически: bbox входа + буфер (параметр).
- **R-GEO-07.** Никакой ручной правки геометрии: всё строится автоматически.

### 3.3. Подход к точке подключения ОКС
- **R-OKS-01.** Полигон `oks` непроходим, вокруг него действует отступ по ДУ (см. таблицу 2).
- **R-OKS-02.** Для полигона, **содержащего** целевую точку, допускается **один финальный прямой отрезок** от ближайшей к точке границы полигона до самой точки. На этот отрезок (включая его часть в зоне отступа) не распространяется отступ к **собственному** полигону. Все остальные ограничения действуют.
- **R-OKS-03.** Если точка вне полигонов, это обычный лист графа.

### 3.4. Присоединение к существующей сети (врезка)
- **R-TIE-01.** Врезка возможна в **любой допустимой точке** существующей линии `heat_network`.
- **R-TIE-02.** Если выбранная точка находится **≤ 10 м** от существующей `heat_chamber` и после подключения у камеры будет **≤ 4** примыканий, используется эта камера (новый участок заканчивается в ней). Если подходят несколько камер, выбираем любую, лучше ту, что даёт минимальный `S`.
- **R-TIE-03.** Иначе в выбранной точке линии создаётся **новая** `heat_chamber`. Существующая линия делится на 2 части, это 2 примыкания + новый участок = 3.
- **R-TIE-04.** Минимального расстояния между новой и существующей камерой нет.
- **R-TIE-05.** Одна связная часть новой сети = одна врезка (см. R-TOP-02).

### 3.5. Неподключённые точки
- **R-UNC-01.** Не подключать точку можно **только** если допустимый маршрут не найден. Сознательно отказываться от подключения ради лучшего `S` **запрещено**.
- **R-UNC-02.** Частичный результат сохраняется, id неподключённых точек выводятся в `unconnected_oks_ids` с исходным типом id.
- **R-UNC-03.** За каждую такую точку начисляется штраф (раздел 6.3).

## 4. Расходы, диаметры, предельная длина

### 4.1. Расход
- **R-FLOW-01.** Расход участка = Σ `flow_tph` всех точек ОКС **ниже по течению** (в поддереве). Считается только подача.
- **R-FLOW-02.** Расход меняется только в узлах ветвления (камерах).

### 4.3. Выбор ДУ
- **R-DN-01.** ДУ участка - **минимальный** из таблицы, у которого `Q_max ≥ flow` **и** выполняется предельная длина (R-LEN).
- **R-DN-02.** Если минимальный по расходу ДУ не проходит по длине, берём следующий, удовлетворяющий обоим условиям. Произвольное завышение ДУ **запрещено**.
- **R-DN-03.** Между соседними узлами, где меняется расход, ДУ **один на всём протяжении**. Менять ДУ только ради сброса счётчика длины **нельзя**.
- **R-DN-04.** От точки ОКС к врезке ДУ **не убывает** (монотонность вверх по дереву).
- **R-DN-05.** Смена ДУ без разветвления возможна только в узле смены расхода. По R-FLOW-02 это камера, значит отдельный `technical_node` для смены ДУ на практике не возникает.

### 4.4. Предельная длина
- **R-LEN-01.** Проверяется **по каждому пути** «точка ОКС → врезка» отдельно.
- **R-LEN-02.** Длина непрерывного фрагмента пути с одинаковым ДУ ≤ `L_max(ДУ)`.
- **R-LEN-03.** Общий участок входит в каждый проходящий через него путь. Параллельные ветки между собой не суммируются.
- **R-LEN-04.** Камера или технический узел **без смены ДУ** счётчик не сбрасывают. **Смена ДУ** начинает новый отсчёт.
- **R-LEN-05.** Длина считается по горизонтальной проекции в EPSG:32637, в том числе в режиме с глубиной.

> Следствие для алгоритма: подбор ДУ идёт снизу вверх по дереву, но счётчик длины зависит от ДУ соседей. Возможен итеративный пересчёт: повышение ДУ на верхнем участке может сделать его равным нижнему и «склеить» фрагменты.

## 5. Пространственные ограничения

### 5.1. Общие правила
- **R-RST-01.** Правило применяется по `restriction_type`, геометрия берётся из объекта.
- **R-RST-02.** Мин. горизонтальное расстояние измеряется **от ограничения до внешней границы габарита** новой сети: ось трубы должна отстоять на `d_min + w(ДУ)/2`.
- **R-RST-03.** Если у ограничения есть собственный габарит (газ, кабель, теплосеть), расстояние считается **между внешними границами двух габаритов**: ось на `d_min + w(ДУ)/2 + w_огр/2` от оси ограничения.
- **R-RST-04.** Внутри разрешённого спецпересечения мин. расстояние **не проверяется**.
- **R-RST-05.** Спецпроход (`laying_method = special`) - **один прямой отрезок**. На его границах участок делится. Если граница не совпадает с камерой или точкой ОКС, ставится `technical_node`.
- **R-RST-06.** Угол пересечения (если задан): для линии - относительно линии ограничения, для полигона - в точке входа спецучастка относительно границы полигона.
- **R-RST-07.** Длина спецучастка за границей полигона отсчитывается вдоль трассы.
- **R-RST-08.** Наложение спецпроходов: на общем фрагменте выполняются **все** геометрические требования, в стоимость идёт **max(K_спец)** (без суммирования и умножения). При смене набора пересекаемых ограничений начинается новый участок.
- **R-RST-09.** Каждое отдельное пересечение одного и того же объекта - отдельный спецпроход.
- **R-RST-10.** В 2D-режиме проверяются только плановые требования. Вертикальные требования действуют только в режиме с глубиной.

## 6. Стоимость и ранжирование

### 6.1. Участки
- **R-COST-01.** Обычный участок: `C = L · c_нов(ДУ) · K_гл`.
- **R-COST-02.** Спецучасток: `C = L · c_нов(ДУ) · K_гл · K_спец`.
- **R-COST-03.** `L` - длина по горизонтальной проекции в EPSG:32637. Если параметры меняются по длине, части считаются отдельно.
- **R-COST-04.** В 2D-режиме `K_гл = 1`.

### 6.2. Камеры и врезки
| Наибольший ДУ примыкающих участков | Новая камера, руб. |
|---|---:|
| 50-200 | 3 000 000 |
| 250-500 | 5 000 000 |
| 600-1000 | 8 000 000 |
| 1200-1400 | 12 000 000 |

- **R-CH-00.** Камера (новая и существующая) - **условная точка**: собственных габаритов нет, отступы от ограничений и площадь под неё не считаются. Проверяются только габариты примыкающих труб.
- **R-CH-01.** `diameter` новой камеры = max ДУ **всех** примыкающих участков, **включая существующие** (при врезке в линию ДУ 400 камера получает ≥ 400, то есть 5 млн). *Подтверждено: берём максимальную трубу.*
- **R-CH-02.** Стоимость новой камеры **включает** присоединение: отдельная плата за врезку не добавляется.
- **R-CH-03.** Врезка в **существующую** камеру стоит 5 000 000 руб. за каждый новый линейный участок, заканчивающийся в ней.
- **R-CH-04.** Камеры ветвления внутри новой сети - тоже новые камеры со стоимостью по таблице.

### 6.3. Итог варианта
```
construction_cost   = Σ C_участков + Σ C_новых_камер + Σ C_врезок_в_существующие
unconnected_penalty = Σ (100 000 000 + 500 000 · G_i)        // G_i = flow_tph неподключённой точки
calculated_cost  C  = construction_cost + unconnected_penalty
new_network_length L = Σ длин новых участков, м
S = 0,7 · (C / 25 000 000) + 0,3 · (L / 100)                 // меньше - лучше
```
Проверка на примере из приложения: 100 м ДУ100 = 8 974 800 + врезка 5 000 000 = 13 974 800, `S = 0,7·0,55899 + 0,3·1 = 0,6913` ✓

### 6.4. Полезные производные (для весов графа)
- Вклад 1 м трассы в `S`: `ω(ДУ, K) = 0,7 · c_нов(ДУ) · K / 25 000 000 + 0,003`. Для ДУ100 это ≈ 0,00251 + 0,003, то есть **длина весит не меньше стоимости**, и короткий путь почти всегда выгоднее.
- 1 камера за 3 млн ≈ 0,084 по `S` ≈ 16 м трассы ДУ100. Камера за 5 млн ≈ 0,14 ≈ 25 м.
- Для врезки в линию с ДУ 250-500 новая камера (5 млн) стоит **столько же**, сколько врезка в существующую камеру (5 млн). При линии ДУ ≤ 200 новая камера (3 млн) **дешевле**.
- Объединение ОКС в общую ветку экономит длину, но добавляет камеру ветвления (≥ 3 млн) и повышает ДУ общего участка. Это главный компромисс оптимизации.

### 6.5. Варианты
- **R-VAR-01.** В каждом режиме - до 3 **содержательно разных** вариантов: другая врезка, другое объединение ОКС, другой маршрут, другое разбиение на части, другой способ прохода ограничения.
- **R-VAR-02.** Небольшое смещение той же трассы вариантом **не считается**. Нужна метрика различия (параметр).
- **R-VAR-03.** Все варианты ранжируются в одном списке по `S`, `rank = 1` у минимального.
- **R-VAR-04.** 2D-режим и режим с глубиной ранжируются **раздельно**, в разных файлах.

## 8. Режим с глубиной (дополнительная задача, необязательная)

Отдельный расчёт со своим набором вариантов и своим ранжированием. Маршрут может отличаться от 2D.

| Параметр | Значение |
|---|---|
| Поверхность земли | горизонтальная, Z = 0 |
| Глубина | до **верха габарита** новой сети |
| Обычная глубина | 3,0 м |
| Минимальная глубина | 0,7 м |
| Максимальная глубина | не ограничена |
| Шаг по глубине | не задан (непрерывный) |
| Макс. уклон | 0,10 м/м (1 м по вертикали требует ≥ 10 м по горизонтали) |
| Профиль при обходе | спуск/подъём → постоянная глубина → (возврат); между близкими препятствиями можно оставаться на изменённой глубине |
| Условная глубина чужих коммуникаций (до верха) | газ 2,8 м; кабель 2,7 м; теплосеть 3,0 м |
| K_гл | `1` при h ≤ 3,0; `1 + 0,10·(h − 3)` при h > 3,0 |
| K_гл на наклонном участке | среднее K_гл на концах; если участок пересекает h = 3,0 м, в этой точке ставится `technical_node` и участок делится |
| Выход | Z-координаты **не нужны**, глубина передаётся через `depth_start`/`depth_end` |
| Нет маршрута | ОКС или часть трассы помечается как требующая ручной проработки |

Вертикальные правила по типам - последний столбец таблицы 2. Высота габарита новой сети берётся из таблицы 1. Проверка «выше»: низ новой ≥ верх чужой + просвет, то есть `h + h_габ(ДУ) + просвет ≤ h_огр`. Проверка «ниже»: `h ≥ h_огр + h_габ_огр + просвет`. Если допустимы оба варианта, выбирается более дешёвый.

## 13. Что покажем на демо и сдадим

**Демо:** загрузка → запуск без ручной подготовки → выгрузка → сеть, врезки, расходы, ДУ, проверка предельной длины, стоимость → работа с ограничениями → влияние на существующую сеть (см. раздел 9) → неподключённые ОКС → сравнение вариантов и ранжирование → алгоритм и границы применимости → (опционально) режим с глубиной.

**Документация:** алгоритм поиска маршрутов и объединения ОКС; обработка ненайденных маршрутов; формат выхода; (опц.) алгоритм с глубиной; границы применимости.

**Промежуточная сдача:** прототип загрузки + автопостроение хотя бы части сети + список рисков и план.

**Критерии оценки:** сначала обязательные правила (сеть, расходы и ДУ, предельная длина, ограничения, выход), затем подход, качество трассировки (число поворотов, без мелкой ломаной и лишних обходов), соответствие задаче, эффективность (стоимость, число врезок и камер, объединение ОКС), техническая проработка (стабильность, диагностика данных, работа на другом наборе), варианты и объяснимость, доп. ценность, питч.
